# Derniers cas limites — résultat indépendant

**Deux lacunes bloquent le parcours nominal : scope existant vide et ajout de demande au plan.** La continuation du flow après changement de graphe fonctionne, mais sa procédure doit être rendue explicite.

Reproduction : `python3 /tmp/forward-release-plan-auvQFI/edges.py /tmp/nouveau-repertoire`. Scripts ciblés du worktree exécutés, tous les fichiers et projets d'essai créés exclusivement sous /tmp. Transcripts séparés dans `edges/transcript.txt` et `edges-confirmation/transcript.txt`.

1. **P1 — un futur module au dossier vide ne démarre pas.** Même définition acceptée par init ; dossier absent : start réussit. Dossier créé mais vide : start échoue « périmètre de code vide », après écriture d'un fichier flow non référencé dans le plan ; status affiche toujours pending/PRÊT. Chaque nouvelle tentative peut ajouter un orphelin. Solution minimale : autoriser une empreinte initiale vide pour start et changed (pas pour la preuve finale), calculer cette empreinte avant toute écriture du flow. La création ultérieure d'un fichier dans le module absent est bien remontée par changed.

2. **P2 — aucune commande d'ajout à un plan existant.** Nouvelle définition T01+T02+T03 : init refuse d'écraser l'historique, à raison ; add est une commande inconnue. Les deux rôles et RELEASE_PLAN ne documentent pas d'édition sûre du plan. Solution minimale : append/add sous verrou, identifiants nouveaux uniquement, rejet des receipts/attempts/deferred entrants, validation du graphe complet des dépendances et événement d'historique motivé. Conserver tâches existantes et réceptions. À défaut, documenter une modification contrôlée du seul tableau tasks, mais cette solution est moins robuste que l'API verrouillée.

3. **Procédure de continuation — mécanisme correct, instructions incomplètes.** Changer le graphe rend status rouge ; release libère tout de même le claim ; migrate refuse une modification sémantique du nœud en attente. Une modification globale éditoriale est migrée et status fonctionne. Une copie d'origine conservée octet pour octet est directement utilisable avec --graph. En revanche sérialiser graph_snapshot puis appeler status échoue car le hash porte sur les octets. Une solution entièrement supportée est : exporter graph_snapshot dans un fichier local figé, libérer les claims, exécuter `odoo_flow.py --graph SNAPSHOT migrate FLOW`, puis passer `--graph SNAPSHOT` à toutes les commandes. La migration vers ce même graphe sémantique est acceptée, sans modifier de hash à la main. Ce parcours complet est éprouvé dans edges-confirmation/transcript.txt. Le README devrait montrer ces commandes ; il ne suffit pas d'écrire « utiliser sa référence figée ».

Limite : aucune opération Odoo réelle ; ces tests concernent les scripts de pilotage. Lors d'une recherche initiale trop large pour localiser la documentation, des extraits quality-lab ont été retournés accidentellement ; aucun n'a servi aux constats ou à ces scénarios, tous fondés sur les sorties locales ci-dessus.
